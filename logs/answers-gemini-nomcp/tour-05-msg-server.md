# How is a message sent on the server side in Rocket.Chat?

## Baseline Answer (no tools)

Sending a message on the server side in Rocket.Chat is a multi-step process handled primarily through a Meteor method that delegates to a core server-side function.

Here's a breakdown of the typical flow:

1.  **Client-Side Initiation and Meteor Method Call:**
    *   When a user types a message and presses Enter (or clicks send), the client-side code (e.g., in `client/views/room/MessageInput/MessageInput.tsx`) prepares the message object.
    *   It then invokes the `sendMessage` Meteor method.

2.  **Meteor Method Handler:**
    *   The server-side entry point for sending a message is typically defined in `app/lib/server/methods/sendMessage.ts`.
    *   This method receives the `rid` (room ID) and `msg` (message content, often including a `_id` generated by the client, `temp` flag, etc.).
    *   It performs initial permission checks (e.g., if the user can send messages in that room) and then calls the core server-side function.

3.  **Core `RocketChat.sendMessage` Function:**
    *   The heart of the message sending logic resides in `app/lib/server/functions/sendMessage.ts`. This function, `RocketChat.sendMessage`, orchestrates the entire process.
    *   It takes the `user`, `message`, and `room` objects as arguments.

4.  **Message Pre-Processing and Validation:**
    *   **Callback Hooks:** `beforeSaveMessage` callbacks are triggered (defined in `app/lib/server/lib/callbacks.ts`). These allow plugins or custom logic to modify or validate the message *before* it's saved. For example, some integrations might preprocess message text.
    *   **Message Validation:** The function calls `validateMessage` (from `app/lib/server/functions/chat/validateMessage.ts`) which performs various checks:
        *   User permissions (can the user send messages in this room?)
        *   Room status (is the room active, not read-only, etc.?)
        *   Message content validation (e.g., length, forbidden characters).
        *   Rate limiting for message sending.
    *   **Message Enrichment and Transformation:**
        *   The message object is enriched with server-side data:
            *   `ts`: Timestamp of when the message was received by the server.
            *   `u`: User object (ID, username, name of the sender).
            *   `_id`: If the client didn't provide one, a new `_id` is generated.
            *   `channel`: If applicable, for federated rooms.
        *   `processMessage` (from `app/lib/server/lib/processMessage.ts`) is called to:
            *   Identify and transform mentions (`@username`).
            *   Parse URLs.
            *   Process Markdown.
            *   Identify hashtags (`#tag`).
            *   Potentially add `urls`, `mentions`, `channels` arrays to the message object.

5.  **Database Insertion:**
    *   After validation and enrichment, the message object is inserted into the `rocketchat_message` collection.
    *   This is done via `RocketChat.models.Messages.insert(message)` (the `Messages` model is defined in `app/models/server/raw/Messages.ts`).

6.  **Post-Insertion Actions and Callbacks:**
    *   **`afterSaveMessage` Callbacks:** Once the message is successfully saved to the database, `afterSaveMessage` callbacks are triggered. These are crucial for various post-processing tasks:
        *   **Notifications:** Sending push notifications, email notifications, or webhook notifications (handled by `app/lib/server/lib/sendNotificationsOnMessage.ts` and related modules).
        *   **Statistics:** Updating message counts for users and rooms.
        *   **Mentions:** Notifying mentioned users.
        *   **Integrations:** Triggering outgoing webhooks for new messages.
        *   **Livechat:** Specific processing for livechat messages.
    *   **Real-time Updates:**
        *   **Subscriptions/Publications:** Since the `rocketchat_message` collection is often published to clients, inserting a new document automatically triggers a DDP (Distributed Data Protocol) update to all subscribed clients in that room.
        *   Clients subscribed to the specific room (via `client/methods/subscriptions/rooms.ts` and associated publications like `app/subscriptions/server/publications/room.ts`) will receive the new message data in real-time. This is how the message immediately appears in everyone's chat window.
    *   **User Status Update:** The `UserPresence` system might update the sender's last activity time.

7.  **Return to Client:**
    *   The `sendMessage` Meteor method returns the `_id` of the newly created message (or the original client-generated `_id` if it was used) to the client, confirming the message was sent.

In essence, the server acts as a central hub that validates, processes, persists, and then broadcasts new messages to all relevant clients and external services.
