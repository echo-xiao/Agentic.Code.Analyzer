# How are the keys managed for end-to-end (E2E) encryption in Rocket.Chat?

## Baseline Answer (no tools)

Rocket.Chat's End-to-End (E2E) encryption key management is a sophisticated system built upon the [OLM library](https://gitlab.matrix.org/matrix-org/olm), which implements a variant of the [Signal Protocol](https://signal.org/docs/specifications/doubleratchet/). It's designed to ensure that only the intended participants can read messages, with the Rocket.Chat server having no access to decrypted content.

Here's a breakdown of how keys are managed:

### 1. User Master Key (UMK) / User Private Key

*   **Generation:** When a user enables E2E encryption for the first time, a unique **User Master Key (UMK)** (also often referred to as the User Private Key) is generated client-side using a cryptographically secure random number generator. This key is the foundation for all other keys associated with that user.
*   **Encryption:** The UMK is immediately encrypted using a key derived from the user's password. This derivation typically uses a strong Key Derivation Function like PBKDF2, ensuring that the UMK is protected even if the local storage is compromised.
*   **Storage (Client-side):** The *encrypted* UMK is stored locally on the user's device:
    *   **Web/Desktop:** In the browser's IndexedDB or local storage.
    *   **Mobile:** In secure storage mechanisms provided by the operating system (e.g., iOS Keychain, Android Keystore).
    *   The *decrypted* UMK is only held in memory while the user is logged in and actively using E2E features.
*   **User Public Key:** A corresponding **User Public Key** is derived from the UMK. This public key is then uploaded to the Rocket.Chat server.
*   **One-Time Prekeys (OTPs):** The client also generates a set of OLM one-time prekeys and uploads their public parts to the server. These are crucial for establishing initial secure sessions with other users without requiring real-time interaction.

### 2. Room Keys (Session Keys)

*   **Generation:** When an E2E-enabled room is created, or a user joins one, a unique **Room Key (or Session Key)** is generated by one of the participants (typically the room creator or the first participant to send a message).
*   **Encryption & Distribution:** This Room Key is then encrypted individually for *each participant* in the room using their respective **User Public Keys** (retrieved from the server).
*   **Storage (Server-side):** These individually encrypted Room Keys are then uploaded to the Rocket.Chat server and stored alongside the room metadata. **Crucially, the server only stores the *encrypted* versions and cannot decrypt them.**
*   **Storage (Client-side):** Each client, upon receiving its encrypted Room Key, decrypts it using its own UMK and stores the decrypted Room Key locally (e.g., in IndexedDB). This allows the client to encrypt and decrypt messages within that specific room.

### 3. Key Storage Summary

*   **Client-side (Encrypted):** User Master Key (UMK).
*   **Client-side (Decrypted):** Room Keys (while in use, and often cached locally for persistence).
*   **Server-side (Public/Encrypted):** User Public Keys, One-Time Prekeys (public parts), and *individually encrypted* Room Keys.

### 4. Device Management

*   **New Device Login:** When a user logs in from a new device, they need to "link" or "verify" it. This process typically involves:
    1.  Logging in with username/password.
    2.  Scanning a QR code displayed on the new device using an *already verified* device, or entering a security code.
    3.  This process securely transfers the encrypted UMK from the verified device to the new device.
*   **Room Key Access:** Once the UMK is on the new device, it can decrypt existing room keys that were previously encrypted for the user. For new messages, new OLM sessions are established with other participants.

### 5. Key Recovery / Security Code

*   **Purpose:** Rocket.Chat provides a **Security Code** (often a mnemonic phrase or a long alphanumeric string) that acts as a recovery key.
*   **Mechanism:** This code is generated when E2E is first enabled and is derived from the UMK. It can be used to decrypt the UMK if the user forgets their password or needs to restore their E2E keys on a new device without an existing verified device.
*   **Importance:** Users are strongly advised to back up this security code in a secure location, as losing both their password and this code would result in permanent loss of access to their E2E encrypted messages.

### Important Considerations

*   **Server Blindness:** The Rocket.Chat server never has access to the decrypted User Master Key or Room Keys. It acts purely as a relay for encrypted key material and messages.
*   **Password Strength:** The security of the E2E encryption heavily relies on the strength of the user's password, as it's used to encrypt the UMK.
*   **Security Code Backup:** The Security Code is the ultimate fallback for key recovery. Its compromise would allow access to all encrypted messages.
*   **Password Change:** If a user changes their password, the UMK needs to be re-encrypted with a new key derived from the new password.

### Relevant File Paths in Rocket.Chat

You can find the core logic for E2E key management in these areas:

*   **Client-side E2E Logic:**
    *   `app/e2e/client/index.js`: Entry point for client-side E2E features.
    *   `app/e2e/client/lib/Olm.js`: Wrapper for the OLM library.
    *   `app/e2e/client/lib/e2e.js`: Contains core E2E functions like key generation, encryption, decryption, and session management.
    *   `app/e2e/client/lib/securityCode.js`: Logic related to the E2E security code.
    *   `app/e2e/client/lib/deviceManagement.js`: Handles linking new devices.
    *   `app/e2e/client/lib/storage.js`: Manages local storage of encrypted keys (e.g., IndexedDB).

*   **Server-side E2E Logic:**
    *   `app/e2e/server/index.js`: Server-side E2E entry point.
    *   `app/e2e/server/methods/e2e.js`: Defines Meteor methods for E2E operations, such as `e2e.setUsersPublicAndOneTimeKeys` (for uploading public keys and prekeys) and `e2e.updateGroupKey` (for uploading encrypted room keys).
    *   `app/e2e/server/publications/e2e.js`: Defines Meteor publications for E2E data, allowing clients to subscribe to public keys and encrypted room keys.
    *   `app/models/server/raw/E2EKeys.js`: The MongoDB collection where public keys, one-time prekeys, and encrypted room keys are stored on the server.

This architecture ensures a robust and secure E2E encryption system where the server never holds the keys to decrypt user communications.
