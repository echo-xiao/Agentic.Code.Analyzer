# How are the keys managed for end-to-end (E2E) encryption in Rocket.Chat?

## Baseline Answer (no tools)

Rocket.Chat's End-to-End (E2E) encryption relies heavily on the **Signal Protocol**, implemented via the `libolm` library (Open Linter Messaging). The key management strategy is designed to ensure that the Rocket.Chat server never has access to the unencrypted private keys or the message content.

Here's a breakdown of how keys are managed:

### 1. Key Types

Rocket.Chat utilizes several types of keys, similar to the Signal Protocol:

*   **Identity Keys (Long-Term):**
    *   Each user has a unique, long-term **identity key pair** (Curve25519).
    *   **Private Identity Key:** Generated client-side (in your browser, desktop app, or mobile app) and *never leaves your device unencrypted*. It's the most critical key.
    *   **Public Identity Key:** Uploaded to the Rocket.Chat server. This allows other users to establish secure sessions with you.
*   **Pre-Keys (Ephemeral):**
    *   These are a set of one-time-use public keys generated by the client.
    *   They are uploaded to the Rocket.Chat server and are used for the initial setup of a secure session with another user.
    *   Once a pre-key is used, it's discarded by the sender and receiver, providing forward secrecy.
*   **Signed Pre-Keys:** A specific type of pre-key that is signed by the user's identity key, providing authenticity.
*   **Session Keys (Ephemeral):**
    *   Derived using the **Double Ratchet Algorithm** for each individual conversation (1:1 or group).
    *   These keys are short-lived and are constantly changing with each message sent, providing forward secrecy and post-compromise security. They are never stored long-term.
*   **Room Keys (Symmetric, for Groups):**
    *   For group chats, Rocket.Chat uses a symmetric AES key (the "room key") for encrypting messages within that specific room.
    *   This room key is then *individually encrypted* for each member of the group using their respective 1:1 OLM sessions.
    *   When a new member joins, the room key is re-encrypted for them. When a member leaves, the room key is rotated (a new one is generated and distributed).

### 2. Key Generation and Storage

*   **Client-Side Generation:** All private keys (identity, pre-keys) are generated directly on the user's device (browser, desktop app, mobile app). The server is never involved in their generation.
*   **Local Storage of Private Keys:**
    *   The user's **private identity key** and other sensitive OLM session state are stored *locally* on the device.
    *   **Crucially, these local keys are encrypted using a key derived from a user-provided passphrase, known as the "E2E password."** This means even if someone gains access to your device's local storage, they cannot decrypt your private keys without your E2E password.
    *   **Storage Mechanisms:**
        *   **Web/Desktop:** Typically stored in `IndexedDB` (a browser database).
        *   **Mobile Apps:** Stored in secure native storage (e.g., iOS Keychain, Android Keystore).
*   **Server-Side Storage of Public Keys:**
    *   The user's **public identity key** and **public pre-keys** are uploaded to the Rocket.Chat server.
    *   The server acts as a "key directory," allowing users to fetch the public keys of their contacts to initiate secure sessions. The server never sees the corresponding private keys.

### 3. The E2E Password

*   This is a critical component of Rocket.Chat's E2E key management.
*   When you enable E2E encryption, you are prompted to set an E2E password.
*   **Purpose:** This password is used to encrypt your private identity key and other sensitive OLM data *before* it's stored locally on your device. It's also used to encrypt your private identity key if you choose to store it on the server for multi-device sync (see below).
*   **Client-Side Only:** The E2E password is *never* sent to the Rocket.Chat server. It's used purely client-side to derive the encryption key for your private data.
*   **Irrecoverable:** If you forget your E2E password, Rocket.Chat cannot recover it for you, and you will lose access to your encrypted message history on new devices or if your local storage is cleared.

### 4. Key Exchange and Session Establishment

1.  **Fetching Public Keys:** When User A wants to send an E2E message to User B, User A's client fetches User B's public identity key and a public pre-key from the Rocket.Chat server.
2.  **Session Setup:** User A's client then uses `libolm` to perform a Diffie-Hellman key exchange with User B's public keys. This establishes an initial secure session.
3.  **Double Ratchet:** Once the initial session is established, the Double Ratchet Algorithm continuously derives new, ephemeral session keys for each message, ensuring forward secrecy.

### 5. Multi-Device Support

Multi-device E2E is complex. Rocket.Chat handles it by:

*   **Device-Specific Identity Keys:** Each device (browser, desktop app, mobile app) where you log in and enable E2E will generate its *own* unique identity key pair.
*   **Linking Devices:**
    *   **E2E Password Re-entry:** When you log in on a new device, you can re-enter your E2E password. If you previously opted to store your *encrypted* private identity key on the server (encrypted with your E2E password), the new device can download it and decrypt it using the password.
    *   **QR Code / Secure Linking:** Rocket.Chat also supports linking new devices by scanning a QR code from an already trusted device. This process securely transfers the private identity key (or a derived key) to the new device without exposing it to the server.
*   **Session Synchronization:** When a message is sent, it's encrypted for *all* active devices of the recipient.

### 6. Key Management Lifecycle Summary

1.  **Enable E2E:** User enables E2E and sets an E2E password.
2.  **Generate Keys:** Client generates private identity key, encrypts it with E2E password, and stores it locally. Public identity key and pre-keys are uploaded to the server.
3.  **Initiate Chat:** When chatting with another user, their public keys are fetched from the server.
4.  **Establish Session:** OLM establishes a secure session using the Double Ratchet Algorithm, deriving ephemeral session keys.
5.  **Encrypt/Decrypt Messages:** Messages are encrypted with session keys (1:1) or room keys (groups) and sent. Upon receipt, the client decrypts using its corresponding session/room key.
6.  **Multi-Device Sync:** New devices are linked by re-entering the E2E password (to decrypt a server-stored, encrypted private key) or via secure device linking.

### Relevant File Paths in the Rocket.Chat Repository

The core E2E logic resides primarily in the `app/e2e` directory:

*   **`app/e2e/client/`**: Contains the client-side implementation for key generation, storage, session management, and encryption/decryption.
    *   `app/e2e/client/index.ts`: Main entry point for E2E client-side.
    *   `app/e2e/client/lib/olm.ts`: Wrapper around `libolm`, handling key generation, session creation, and message encryption/decryption.
    *   `app/e2e/client/lib/keyStore.ts`: Manages the storage and retrieval of encrypted private keys and OLM session data (e.g., to IndexedDB).
    *   `app/e2e/client/lib/crypto.ts`: Utility functions for cryptographic operations, including deriving keys from the E2E password.
    *   `app/e2e/client/lib/roomKeys.ts`: Logic specific to managing symmetric room keys for group chats.
*   **`app/e2e/server/`**: Contains server-side methods and publications for handling public key uploads and distribution.
    *   `app/e2e/server/methods/`: Server methods for users to upload their public keys and pre-keys.
    *   `app/e2e/server/publications/`: Publications to allow clients to subscribe to other users' public keys.

In summary, Rocket.Chat's E2E key management is robust, leveraging established cryptographic protocols and ensuring that the server acts only as a relay and key directory, never having access to the sensitive private keys or the content of your encrypted communications. The user's E2E password is the ultimate guardian of their private keys.
