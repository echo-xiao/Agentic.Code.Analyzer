# How are the keys managed for end-to-end (E2E) encryption in Rocket.Chat?

## Baseline Answer (no tools)

Rocket.Chat's End-to-End (E2E) encryption is built upon the [OLM protocol](https://gitlab.matrix.org/matrix-org/olm/) (a cryptographic ratchet library like those used in Matrix/Element), ensuring that only the sender and intended recipient can read the messages. The server never has access to the unencrypted message content or the private keys.

Here's a breakdown of how E2E keys are managed in Rocket.Chat:

### 1. Key Generation

When a user enables E2E encryption for the first time on a device, the following keys are generated *locally* on that device:

*   **Identity Keys (Master Keys):** These are long-term key pairs (a public identity key and a private identity key) that uniquely identify the user's device for E2E purposes.
    *   The **private identity key** is never sent to the server.
    *   The **public identity key** is uploaded to the Rocket.Chat server and associated with the user's account, so other users can retrieve it to initiate secure sessions.
*   **One-Time Pre-Keys:** A set of ephemeral key pairs generated by each device.
    *   The **public one-time pre-keys** are uploaded to the server.
    *   These are used as part of the initial key exchange (e.g., Extended Triple Diffie-Hellman - X3DH) to establish a secure session without requiring both parties to be online simultaneously.
    *   Each one-time key is used only once and then discarded by the server.

### 2. Key Exchange (Session Establishment)

To start an E2E encrypted conversation between two users (e.g., Alice and Bob):

1.  **Alice initiates a session:** Alice's client fetches Bob's public identity key and one of Bob's unused public one-time pre-keys from the Rocket.Chat server.
2.  **X3DH Key Agreement:** Alice's client uses her private identity key, Bob's public identity key, her own ephemeral key, and Bob's public one-time pre-key to perform a Diffie-Hellman key exchange. This generates a shared secret.
3.  **Session Key Derivation:** From this shared secret, Alice's client derives an initial symmetric **session key**. This session key will be used to encrypt the actual message content.
4.  **First Message Transmission:** Alice encrypts her first message with the derived session key. She also includes her ephemeral public key (used in the X3DH) in the message header (encrypted as part of the OLM payload).
5.  **Bob's Key Derivation:** When Bob receives Alice's message, his client uses his private identity key, Alice's public identity key (obtained from the server or previously exchanged), his private one-time pre-key (that Alice used), and Alice's ephemeral public key (from the message payload) to independently derive the *exact same session key*.
6.  **Double Ratchet Algorithm:** Once an initial session key is established, the Double Ratchet Algorithm (similar to Signal Protocol) is used. With every message sent, the session key evolves, providing forward secrecy (past compromised keys don't compromise future messages) and post-compromise security (a compromised key doesn't prevent future secure communication). This means that a new symmetric key is effectively used for almost every message.

For group chats, the mechanism is more complex but often involves a similar pairwise key exchange to establish a group key, which is then updated using a ratcheting mechanism.

### 3. Key Storage

*   **Private Identity Keys & Ratchet State:**
    *   These are stored *locally on the user's device* (e.g., in `IndexedDB` for web clients, or secure native storage for desktop/mobile apps).
    *   **Crucially, these are encrypted using a passphrase provided by the user.** This passphrase is never sent to the server. Without it, the client cannot decrypt the stored private keys or session state, rendering E2E messages unreadable from that device.
*   **Public Identity Keys:** Stored on the Rocket.Chat server in the `rocketchat_e2e_keys` collection, associated with the user's device.
*   **Public One-Time Pre-Keys:** Also stored on the Rocket.Chat server in the `rocketchat_e2e_keys` collection, but deleted after they are used in a key exchange.
*   **Session Keys (Symmetric):** These are never persistently stored directly. Instead, the necessary "ratchet state" (which allows the derivation of the current and future session keys) is stored locally, encrypted by the user's passphrase.

### 4. Key Recovery and Backup

*   **Passphrase:** The user's passphrase is the primary defense for their local private keys. Forgetting this passphrase means the user will lose access to their E2E message history on that device and won't be able to initiate new E2E conversations from it without generating new keys.
*   **Recovery Key:** When E2E is first enabled, users are usually prompted to download a "recovery key" (typically a JSON file). This file contains an encrypted backup of their private identity keys and the salt used for their passphrase. This recovery key is essential for:
    *   Restoring E2E access on a new device.
    *   Recovering access if the original device is lost or compromised.
    *   **The server has no means to recover a user's private keys or message history.** This design choice is fundamental to true E2E encryption.

### Relevant Code Paths:

*   **Client-side E2E logic (key generation, storage, encryption/decryption):**
    *   `app/e2e/client/`
    *   `app/e2e/client/lib/olm.js`: Wrapper around the OLM library (often compiled from C++ to WebAssembly).
    *   `app/e2e/client/lib/e2e.js`: Contains the core logic for key management, session handling, message encryption/decryption.
    *   `app/e2e/client/lib/deviceManagement.js`: Handles device key management and storage.
    *   `app/e2e/client/lib/storage.js`: Handles local storage (e.g., `IndexedDB`) of encrypted private keys and session data.
*   **Server-side API for public key management:**
    *   `app/e2e/server/`: Contains server-side methods and publications for interacting with public keys.
    *   `app/e2e/server/methods/e2e.js`: Provides DDP methods for clients to upload their public identity keys and one-time pre-keys, and to claim one-time keys during key exchange.
    *   `app/e2e/server/publications/e2eKeys.js`: Publishes public keys to clients.
*   **Database Collection:**
    *   `rocketchat_e2e_keys`: Stores public identity keys and public one-time pre-keys.

In summary, Rocket.Chat's E2E key management adheres to strong cryptographic principles, leveraging local, passphrase-protected storage for private keys and a robust key exchange mechanism (OLM/X3DH with Double Ratchet) to ensure message confidentiality. The server's role is strictly limited to facilitating the exchange of public keys and encrypted messages, without ever having access to the private cryptographic material.
